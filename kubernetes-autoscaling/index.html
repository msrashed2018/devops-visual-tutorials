The simplest mental model

Kubernetes autoscaling works at different layers. The biggest mistake is thinking there is only one “autoscaler”.

1

HPA: change the number of Pods

Traffic rises → run more replicas. Traffic drops → run fewer replicas.

4 Pods → 8 Pods
2

VPA: change the size of Pods

A Pod needs more CPU/RAM → increase its resource request.

500m CPU → 1000m CPU
3

Node autoscaling: change cluster capacity

Pods cannot fit → provision more worker Nodes.

3 Nodes → 5 Nodes
⚙️ Horizontal Pod Autoscaler

HPA changes the replica count

HPA is a Kubernetes API resource plus a controller. It periodically reads metrics, compares them with your target, calculates a desired replica count, and updates the target workload.

💡 In simple words: HPA keeps asking: “Are my current Pods busy enough that I should add more, or quiet enough that I should remove some?”

Where do HPA metrics come from?

Resource metrics

CPU and memory, typically exposed through Metrics Server / Metrics API.

metrics.k8s.io

Custom metrics

Application-specific metrics, such as requests per second.

custom.metrics.k8s.io

External metrics

Metrics outside the cluster, such as queue depth.

external.metrics.k8s.io

Object metrics

A metric describing another Kubernetes object or external resource.

A practical HPA example

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60

Here Kubernetes tries to keep average CPU utilization around 60%, while keeping the Deployment between 2 and 20 Pods.

⚠️ Important: CPU utilization is calculated relative to the Pod's CPU requests. Bad resource requests often lead to bad scaling decisions.

The simplified replica formula

desired replicas ≈ ceil(current replicas × current metric / desired metric)

Example: 4 Pods at 90% CPU, target is 60% → roughly 6 desired Pods. Kubernetes also applies readiness handling, tolerances, stabilization windows, and scaling policies.

📐 Vertical Pod Autoscaler

VPA rightsizes CPU and memory

VPA adjusts a workload's CPU and memory requests/limits based on actual usage. It is useful when you want Kubernetes to help answer: “How big should each Pod be?”

HPAchanges how many Pods
VPAchanges how large each Pod is

Unlike HPA, VPA is not part of the core Kubernetes API installation. It uses a CRD and must be installed separately. The stable VPA API is autoscaling.k8s.io/v1.

💡 Production tip: Teams often run VPA in recommendation-only mode first, inspect the suggestions, and only later allow automatic updates.

🔄 The full production loop

How the layers cooperate

1Traffic risesUsers send more work.
2Metrics riseCPU, RPS, queue depth, etc.
3HPA adds replicasDeployment replica count increases.
4Pods may stay PendingExisting Nodes have no space.
5Node autoscaler adds NodesCloud capacity is provisioned.
6Scheduler places PodsApplication capacity catches up.
🎯 Rule of thumb: HPA scales the application; node autoscaling scales the cluster capacity.

Scale-to-zero

Modern Kubernetes can scale suitable HPA workloads to zero with object or external metrics when the relevant feature is available and enabled. It is especially useful for queue-driven or event-driven workloads.

⚠️ Cold-start caveat: Kubernetes Services do not buffer HTTP requests while there are zero ready Pods. A request-driven scale-to-zero design needs buffering or a component that can tolerate startup delay.
💼 Production engineering notes

What senior engineers should care about

✅ Set realistic resource requests

They affect scheduling and HPA CPU utilization calculations.

✅ Scale on the metric that reflects demand

CPU is not always the best signal. Queue depth or RPS can be better.

✅ Protect scale-down

Use stabilization windows and conservative policies to avoid thrashing.

✅ Test cold starts

Autoscaling only helps if your application can start quickly enough.

✅ Plan for capacity limits

Cloud quotas, Node constraints, zones, and instance availability can block scale-out.

✅ Combine with disruption controls

Graceful shutdown and PodDisruptionBudgets help maintain availability.

Common mistakes

  • Using HPA without Metrics Server or the needed metrics adapter.
  • Expecting HPA to add worker Nodes.
  • Setting CPU requests far too low, making utilization look artificially high.
  • Scaling on CPU for queue-driven work when queue depth is the real demand signal.
  • Setting minReplicas too low without considering cold starts.
  • Running HPA and VPA against the same signal without understanding their interaction.
🎓 Interview cheat sheet

Questions you should be able to answer

What is the difference between HPA, VPA, and node autoscaling?

HPA changes replica count; VPA changes Pod resource sizing; node autoscaling changes the number/capacity of Nodes.

Why do resource requests matter to HPA?

For CPU utilization targets, HPA compares current CPU usage against requested CPU. Incorrect requests distort utilization.

What happens when HPA creates more Pods but the cluster is full?

The Pods stay Pending. A node autoscaler can detect unschedulable Pods and provision more Nodes if configuration, quotas, and cloud capacity allow it.

Can HPA scale a DaemonSet?

No. HPA targets scalable resources that expose the scale subresource; DaemonSets are not horizontally scaled that way.

When is CPU a bad scaling metric?

When workload demand is better represented by a business/application signal such as queue depth, active requests, latency pressure, or jobs waiting.
